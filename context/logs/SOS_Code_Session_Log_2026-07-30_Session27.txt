2. INVOICE RESET PATH - BUILT AND PROVEN
Before running the smoke test we built a cleanup path, because a failed POST
would otherwise leave PVS records flipped to Final and linked to a dead invoice
with no way back.
DECISION LOCKED: We VOID, we never DELETE. In Creator and in Books. Neil's
reasoning: preserve every record generated, and see every Books action inside
the app the same way it appears in Books. Void keeps the record and the invoice
number and stops it counting toward money owed. Delete destroys the audit trail
and lets the number be reused.
Books has a void endpoint separate from delete:
  POST /books/v3/invoices/{invoice_id}/status/void
DECISION: failed batch records stay Failed. A retry means a NEW Invoice_Batch
record. Each batch record is the record of one attempt. Rejected the alternative
of resetting a batch to Pending for re-save, because the On Success workflow
fires on Created only, so making it re-fire would require changing the record
event to Created or Edited - and then any accidental edit of an old batch record
could double-invoice a branch.
reset_invoice was run three times, all clean:
  INV-000002 voided, PVS-1007-NH returned to Draft
  INV-000003 voided, PVS-1008-NH returned to Draft
  INV-000004 voided, PVS-1007-NH returned to Draft

5. THE SECTION VISIBILITY BUG - ROOT CAUSE
Saved PVS records were opening with the Clinical, Procedure, Cost Drivers,
Charges, Diversion and Files sections all missing. Default Hide On Load runs on
ADD OR EDIT and hides every section. Entry Type Section Visibility, which shows
them back, runs on ADD ONLY and only on user input of Type_of_Entry. So
reopening any saved PVS hid everything and nothing ever restored it.
This is a whole CLASS of bug in this app: any field or section hidden on load
and re-shown only by an on-user-input workflow is invisible forever on a saved
record. Fixed for sections, Facility fields, Type_of_Diversion, and the
Equipment / Other charge fields. Watch for more of the same pattern.

6. THE INVOICE CONNECTION MYSTERY - NOT A CODE BUG
Invoice Connection looked permanently blank on the PVS. It was storing correctly
the whole time and only RENDERING blank. Encounter_PatientVisit.Invoice_Link had
display format = Invoice_ID. Invoices.Invoice_ID is a field nothing ever
populates. Invoice_Batch.Invoice_Link uses Books_Invoice_Number, which is why
that one always displayed.
FIX: changed the PVS Invoice_Link display format to Books_Invoice_Number. Field
property change only, no code, no data change. Confirmed working - PVS-1007 now
reads INV-000004 and Invoice Status reads Final.
LESSON, AND IT COST US AN HOUR: a Creator lookup with an empty display-format
field renders blank even when the ID is stored. Do not diagnose from the form.
Neil's standing rule was right - data questions need a diagnostic function or a
report column, not inference from the UI.
A wrong turn worth recording: I diagnosed the blank as bare field assignment
failing to persist inside a for-each loop and rewrote the update loop on that
basis. reset_invoice then found the linked PVS on every invoice, which proved
the assignment HAD persisted and the diagnosis was wrong. The explicit update
statement is still the documented and correct form, so the rewrite stays - but
the reason given for it was wrong.

10. CREATOR v6 GOTCHAS LEARNED TODAY
  - A lookup whose display-format field is empty renders BLANK even when the
    record ID is correctly stored. Check the display format before debugging the
    code.
  - A field or section hidden by an on-load workflow and re-shown only by an
    on-user-input workflow will never reappear on a saved record.
  - Creator cannot prompt for function arguments. To run a function that takes
    arguments, wrap it in a temporary no-arg function.
  - The documented way to update records in a loop is an explicit update
    statement: for each r in Form[criteria] { update r [ Field=value ]; }
  - Deluge subString(start) takes an optional end index. indexOf returns -1 when
    not found.
  - Repo filenames do not always match live Creator workflow link names.
  - Books line item: name max 100 chars, description max 2000 chars, item_id
    documented as required but NOT enforced in practice.
