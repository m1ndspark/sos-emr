================================================================================
2. ROOT CAUSE, FOUND AND FIXED
================================================================================

The On Create workflow on Referrals_Main ran a 15,012 character body that
inserted an Assignments record partway through. Assignments.Patient_DOB is
type text with maxchar 11. The insert wrote a longer value, overflowed, and
terminated the script.

Creator runs a form workflow inside a transaction. The overflow rolled back
every record write in that transaction, including the Referral_ID stamp. It
could not roll back the ZeptoMail send, which had already fired. The email
therefore quoted a Referral ID that no longer existed after the rollback.

Two defects, both fixed:
  a. The Assignments insert now writes MM/dd/yyyy text, which fits in 11.
  b. The notification is no longer sent before the record is committed.

Correction on record: I first misdiagnosed this as a bare assignment syntax
problem. That was wrong. The transaction rollback is the cause.

3. process_new_referral - THE SINGLE CREATE PATH
================================================================================

The entire On Create body was extracted into one function so the create path
and any repair path can never drift.

  Function: process_new_referral
  Language: Deluge, namespace default
  Return:   string
  Args:     string p_refKey, string p_notify

Takes a custom ID such as REF-1080, never a numeric record ID.

Behavior:
  - Resolves the key to a record, returns SKIP-NOTFOUND if there is none.
  - Captures Partner_Branch_Submitted before resolution overwrites the label,
    so the submitted value and the resolved value are both retained.
  - Mints Referral_ID only when blank.
  - Derives Referral_Date from Added_Time, and ONLY for form origin records.
    There is no fallback. If there is no trusted arrival date, nothing is sent
    and nothing is stamped.
  - Commits Referral_Date and Notified_Time FIRST, then sends, then reverts
    both to null if every notifier failed.

The On Create workflow body is now one line:
    thisapp.process_new_referral(input.ID.toString(),"YES");

  Form: Referrals_Main | Record event: On Add | Form event: On Success

4. sos_referral_health - ONE FUNCTION THAT AUDITS EVERY ROW
================================================================================

Replaces the one function per defect approach that was burning Neil's time.

  Function: sos_referral_health
  Args:     string p_mode, string p_scope, int p_limit
  Modes:    REPORT, FIX, FIX_NOTIFY
  Scope:    ALL, a single issue code, or a comma separated list

Issue codes:
  NOID, NOSTAMP, NOPARTNER, NOASSIGN, UNNOTIFIED, NONOTIFIER, NODOB, BADDOB,
  NOPOCEMAIL, TESTREC

Write gate: a referral is skipped only if it has been billed, tested as
Encounter_PatientVisit[Invoice_Link != null]. Unbilled and unbatched rows are
all repairable. TESTREC rows are counted but never repaired.

Blank p_scope returns SKIP-NOSCOPE. This REVERSED the old documented behavior
where blank meant ALL. A blank scope is almost always a forgotten argument,
and the old default turned that into a silent full table write.

Known limit: FIX rescans the whole table on every invocation, so limit 2 is
stable and limit 5 times out with a database operation error. REPORT ALL runs
fine at any limit.

6. STANDING RULE ADDED - DATA PROVENANCE
================================================================================

Every data point in any output, email, report, page, Word file, PDF, module,
anything, must be read directly from Creator at the moment of output. Never
from a remembered, computed, or inferred value. Referral IDs in particular
come only from Creator. If no ID exists, the output says so rather than
supplying one.

Related rule, also added: never infer anything about what exists in the .ds or
the local repo. Every statement about a field, form, workflow, or function
comes from re-reading the current .ds in that moment, reading the full
artifact end to end, not a partial excerpt. This came from a miss where I read
the first 2,200 characters of build_3008_email_html and inferred the rest,
then flagged a phone formatting loop as new when it had been in place for days.

================================================================================
8. THE TWO DOB FIELDS - SETTLED
================================================================================

Referrals_Main carries two DOB fields and neither can be deleted.

  Patient_DOB   type date, display name "Patient DOB (system)", private,
                personal data. THIS IS THE ONE TRUE SOURCE.
  Patient_DOB1  type text, maxchar 11, display name "Patient DOB". Its ONLY
                purpose is to receive the text date from the Zoho Form.

Neil's ruling, verbatim in effect: every Creator report pulls Patient_DOB from
Referrals_Main. Period. Patient_DOB1 exists only to catch the form text, and
Creator parses it into Patient_DOB. If any report shows a DOB it comes from
Patient_DOB.

parse_patient_dob handles MM/DD/YYYY, M/D/YYYY and YYYY-MM-DD, validates month,
day, leap years, and a year range of 1900 to the current year. It rejects two
digit years, text month names, and compact 8 digit strings. None of those
appear in the current data.

11. CREATOR V6 AND DELUGE FACTS LEARNED THIS SESSION
================================================================================

- containsKey does not exist. The Map key test is containKey, no s.
- A form workflow runs in a transaction. Any later error rolls back every
  record write in it. An external call already made, such as a ZeptoMail send,
  cannot be rolled back.
- A maxchar overflow terminates the insert and rolls back the whole script.
- getHour() returns 24 hour format in the app timezone. toDate() accepts a
  date time directly.
- Creator v2.1 meta APIs expose applications, sections, forms, reports, pages
  and fields only. No workflows, functions or Deluge.
- Encounter_PatientVisit.Patient_Phone is type phonenumber. The matching
  Referrals_Main.Patient_Phone is plain text. Cross writes need toString().
- Both Patient_Address fields use the same subfield names: address_line_1,
  address_line_2, district_city, state_province, postal_Code.
- Invoice_Status values are Draft and Final only, so != "Final" admits blank
  imported rows and == "Draft" would not.
- Two Referral_ID formats coexist: legacy REF-MMDDYY-NNNN and current
  REF-NNNN.
