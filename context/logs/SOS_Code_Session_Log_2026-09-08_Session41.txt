3. ROOT CAUSE - DOB MISSING ON EVERY NON-3008 REFERRAL

Every Patient Visit and Imaging Order referral from REF-1109 onward
arrived with no DOB at all.

Ruled out in order: the Creator mapping target (correct, pointed at
Patient_DOB1), the Forms question (only one exists), the field's own
visibility (Show, mandatory), and the grid's default visibility (not
hidden in the Builder).

Actual cause: Patient DOB sat inside a grid that was named as the target
of the 3008 rule's SHOW action. Zoho Forms hides such a grid at runtime
until the rule fires. SSN rendered because it sits outside that grid.

Neil fixed it by adding a second Forms rule covering Patient Visit and
Imaging Order. Verified working.

LESSON TO CARRY FORWARD: in Zoho Forms, naming a field or grid as the
target of a rule's Show action implicitly hides it at runtime by default,
regardless of what the Builder shows for that field's own visibility.

5. DATA ISSUES GUARD - NEW

ARCHITECTURE (after the refactor - see section 14)

New function: compute_data_issues(int p_recId) -> String
  The single source of truth for the rule set. Returns the joined issue
  list, or an empty string when the referral is clean. Every caller uses
  this and nothing else holds the rules.

New workflow: Referral Data Issues Check
  Referrals_Main, Created, On Success.
  Calls compute_data_issues, writes Data_Issues, and emails
  neil.heird@sosmmc.com. Subject "REF Data Issue: [Patient] - [REF-ID]".

New workflow: Referral Data Issues Sync On Edit
  Referrals_Main, Edited, On Success.
  Calls compute_data_issues and writes Data_Issues only when the computed
  value differs from what is stored. That comparison is the loop guard.
  No email on edit - Neil is the one editing, so a notification would be
  noise.

Function: backfill_data_issues(string p_mode) -> String
  PREVIEW / COMMIT. Calls compute_data_issues per record. Idempotent;
  clears the flag when nothing is wrong.

DESIGN DECISION: flag-and-notify, not On Validate block. A blocking
validation would reject a partner's submission outright - the same
failure mode as the referral that went missing on 09-05. A referral
always lands; the gap gets flagged.

14. DATA ISSUES REFACTOR - DONE AT THE END OF THE SESSION

Problem Neil identified: if a referral came in without a DOB and he later
added one, Data_Issues stayed stale. Referral Data Issues Check fires on
Created only, and Referral DOB Sync On Edit does not touch Data_Issues.

The rule set was also duplicated in two places - the create workflow and
backfill_data_issues - and would drift.

Refactor, approved and completed in four parts:

  1. compute_data_issues(int p_recId) -> String   NEW FUNCTION
     Holds the entire 20-check rule set. Returns the joined flag or "".
  2. Referral Data Issues Check (Created, On Success)   REWRITTEN
     Now just calls compute_data_issues, writes, and emails.
  3. Referral Data Issues Sync On Edit (Edited, On Success)   NEW
     Recomputes on every edit; writes only when the value changes.
  4. backfill_data_issues   REWRITTEN
     Calls compute_data_issues per record.

REGRESSION CHECK: PREVIEW after the refactor returned
  records=347 | flagged=1 | cleared=3 | unchanged=343
Every previously flagged record came back unchanged, proving the function
produces identical output to the inline version. The 3 cleared were

RULE GOING FORWARD: the rule set lives in compute_data_issues and nowhere
else. To add or change a check, edit that function only - all three
